The R1 operation runs in this order:

1. PreSync quiesce stops writers and datastores; PreSync restore verifies and restores the selected backup, recording nonterminal `restored`.
2. Sync starts the old datastores and writers. A later apply failure still invokes SyncFail containment and scales writers to zero.
3. PostSync smoke runs with `MODE=restore` and the same restore inputs. It requires the restore receipt, checks API/WS health and the existing subscriber's HMAC inbox session, then records terminal `recovered`. It does not require upgrade index/workflow receipts or alter TTL; the saved baseline starts Mongo with TTL enabled. A validation failure leaves the operation nonterminal for SyncFail containment.
4. Verify old web login, topics, bridge and Mailpit; record recovery time and lost/replayed work, then complete the mandatory hook retirement below before ordinary syncs resume.

Retain the original immutable backup. Never merge this template with unresolved pins, blindly reset receipts, or auto-loop restore.

Recovery is not finished until a reviewed follow-up change retiring the separate R1 source/hooks has merged and the parent has reconciled the Application. Before ordinary syncs resume, remove the second `applications/novu-restore-staging` source, return the complete saved baseline chart source to `spec.source`, and remove restore-only values/inputs. Keep auto-sync disabled throughout; preserve baseline values, ConfigMap receipts and the immutable backup, and archive Job/Pod status and logs before retirement. Setting the 3.19 chart's `upgrade.enabled:false` does **not** remove this separate R1 source.

A repeated restore Pod must acquire both RWO mounts before it can read and skip its completed receipt; with recovered datastores running, it can wait in Multi-Attach until its deadline. The runner's terminal `recovered` guard (backed by the completed PostSync smoke receipt) prevents a later failure hook from re-containing that owner, but cannot prevent the mount deadlock or replace mandatory retirement.
